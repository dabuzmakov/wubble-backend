# Wubble — backend HTTP-мониторинга

Реализован полный путь: пользователь создаёт Monitor, добавляет HTTP Check,
запускает её вручную или по расписанию, получает результат, историю, статистику
и инциденты. Все API-маршруты без версий. Frontend для выполнения проверок не нужен.

## Что входит

- CRUD Monitor и HTTP Check; несколько Check могут иметь один URL.
- Авторизация Bearer JWT; доступ только владельцу Monitor, чужие объекты дают 404.
- GET и HEAD, один ожидаемый HTTP-код, необязательная проверка текста в ответе.
- Ручной запуск, фоновое расписание, пауза и возобновление.
- История с пагинацией и фильтром периода, подробности результата и статистика.
- Инциденты: по умолчанию открытие после 3 подряд неудач, закрытие после 1 успеха.
  Оба порога настраиваются для каждой Check, диапазон 1–10.
- Email владельцу о начале и завершении инцидента, если он включил уведомления у Monitor.
- Защита от SSRF, ограничения таймаута и размера тела, защита от параллельного запуска.
- EF Core-миграция, OpenAPI, примеры запросов и интеграционные проверки.

## Запуск

Требуются .NET SDK 10 и Docker. Команды выполняются из корня распакованного проекта.

```sh
docker compose up -d
dotnet tool restore
dotnet restore Wubble.slnx
dotnet dev-certs https --trust
dotnet user-secrets set "Jwt:SigningKey" "<случайный секрет минимум 32 байта>" --project Wubble.Api
dotnet ef database update --project Wubble.Api
dotnet run --project Wubble.Api --launch-profile https
```

API: https://localhost:7051. Scalar: https://localhost:7051/scalar.
OpenAPI JSON в Development: https://localhost:7051/openapi/v1.json.
`v1` здесь — имя документа OpenAPI; бизнес-маршрутов `/api/v1/...` нет.
Сборка также генерирует документ, без подключения к БД и без секретов.

Зарегистрируйтесь через `/api/auth/register`. Письмо появится в Mailpit:
http://localhost:8025. Пока frontend не запущен, скопируйте `userId` и `token`
из ссылки и передайте их в `/api/auth/verify-email` через Scalar или HTTP-клиент.
После `/api/auth/login` возьмите JWT из `Set-Cookie: wubble_access=...` и вставьте
его в Bearer-авторизацию Scalar. Маршруты мониторинга читают JWT только из заголовка.

Параметры PostgreSQL и Mailpit для разработки уже есть в
`appsettings.Development.json`. Для рабочего окружения задайте
`ConnectionStrings__Default`, `Jwt__SigningKey` и SMTP-настройки из README_AUTH.md.
Письма отправляются от `wubble@alisaboules.ru`; в локальном режиме — в Mailpit.

Миграция `AddMonitoring` добавляет Monitors, Checks, CheckResults, Incidents,
IncidentNotifications и индексы. Примените её также к уже существующей БД Wubble.

## Маршруты

Для краткости в таблице `M` = `/api/monitors/{monitorId}`,
`C` = `/api/monitors/{monitorId}/checks/{id}`.

| Метод | Маршрут | Назначение |
|---|---|---|
| POST | /api/monitors | Создать Monitor |
| GET | /api/monitors | Список своих Monitor со сводкой состояний |
| GET | /api/monitors/{id} | Monitor и сводка его Check |
| PUT | /api/monitors/{id} | Имя, описание, включение email-уведомлений |
| DELETE | /api/monitors/{id} | Удалить Monitor вместе с его данными |
| GET | /api/monitors/{id}/incidents | Инциденты всех Check этого Monitor |
| POST | M/checks | Создать HTTP Check |
| GET | M/checks | Список Check |
| GET | C | Настройки и состояние Check |
| PUT | C | Полностью обновить настройки Check |
| PATCH | C/state | Пауза/возобновление: `{"isEnabled":false}` |
| DELETE | C | Удалить Check и её историю |
| POST | C/run | Выполнить сейчас и вернуть сохранённый результат |
| GET | C/results | История запусков |
| GET | C/results/{resultId} | Один результат |
| GET | C/statistics | Сводка за период, по умолчанию последние 7 дней |
| GET | C/incidents | Инциденты Check |

Списки принимают `page=1&pageSize=20`, максимум pageSize=100, page=100000.
Ответ: `items`, `pageNumber`, `pageSize`, `totalCount`.
История и статистика принимают `from` включительно и `to` исключительно,
например `2026-11-01T00:00:00Z`. Смещения часовых поясов приводятся к UTC.
Списки инцидентов принимают `isOpen=true` или `false`; без фильтра видны все.

Основные ответы: 201 при создании, 200 при чтении/изменении/запуске,
204 при удалении, 400 при неверных параметрах, 401 без действующего JWT,
404 для отсутствующего или чужого объекта. На странице Scalar есть Bearer-схема
и отметки защищённых операций.

Запуск уже выполняющейся Check, её изменение, пауза или удаление дают 409
с `code=already_running`. Удаление Monitor с выполняющейся Check тоже даёт 409.
При заполнении общего лимита запусков — 503 `capacity_reached`.
Для ручного запуска действует лимит 30 запросов в минуту на пользователя (429).
В одном Monitor допускается до 100 Check (409 `check_limit`).

## Пример

Создайте Monitor через `POST /api/monitors`:

```json
{
  "name": "My Shop",
  "description": "Проверки интернет-магазина",
  "emailNotificationsEnabled": false
}
```

Используйте его `id` для `POST /api/monitors/{monitorId}/checks`:

```json
{
  "name": "Главная страница",
  "url": "https://example.com/",
  "method": "GET",
  "intervalSeconds": 300,
  "timeoutSeconds": 10,
  "expectedStatusCode": 200,
  "bodyContains": "Example Domain",
  "failureThreshold": 3,
  "recoveryThreshold": 1,
  "isEnabled": true
}
```

Вызовите `POST /api/monitors/{monitorId}/checks/{id}/run` с Bearer-заголовком.
Тело запроса не требуется. В ответе будут `outcome`, `statusCode`, `durationMs`,
время начала/завершения, тип запуска, `errorCode` и безопасное описание ошибки.
Готовая последовательность запросов для Rider/Visual Studio —
`Wubble.Api/Monitoring.http`. Пример с example.com служит иллюстрацией;
содержимое стороннего сайта может измениться.

## Принятые правила первого варианта

- IntervalSeconds: 60–86400, по умолчанию 300. TimeoutSeconds: 1–30, по умолчанию 10.
- Check создаётся активной; первый автоматический запуск — на ближайшей итерации
  планировщика. Для первоначального ручного теста можно создать её с isEnabled=false.
- Следующий автоматический запуск назначается через интервал **после завершения**
  предыдущего. Ручной запуск активной Check тоже сдвигает следующее выполнение.
- Приостановленную Check разрешено запускать вручную. Такие результаты сохраняются
  и влияют на статистику и инциденты наравне с автоматическими.
- После рестарта выполняется одна просроченная проверка. Очередь пропущенных интервалов
  не воспроизводится. Зависшая lease истекает через timeoutSeconds + 60 секунд.
- RunLeaseId хранится в БД. Два процесса или два пользователя не выполнят одну Check
  одновременно в пределах действующей lease. Устаревший результат не заменит результат
  более нового запуска. Изменения настроек и удаления согласованы с захватом lease.
- При аварийном завершении процесса или недоступности БД отдельный результат может
  не сохраниться. Пропуск не считается ни успешной проверкой, ни доказанным сбоем сайта.
- PUT сбрасывает текущий статус в Unknown и счётчики последовательных результатов.
  История сохраняется. Уже открытый инцидент сохраняется до подтверждённого восстановления.
  Настройки старых запусков отдельно не версионируются.
- Пауза не закрывает инцидент. Длительность инцидента — наблюдаемый период между
  подтверждённым сбоем и восстановлением, включая перерывы; это не точное время простоя.
- Удаление Monitor/Check каскадно удаляет результаты и инциденты. Автоматическая очистка
  истории по сроку хранения пока не включена.

Состояния Check: Unknown — нет актуального результата, Up — последний запуск прошёл,
Down — цель не прошла проверку, Error — выполнение запрещено или произошла внутренняя
ошибка Wubble. Для выключенной Check API показывает Paused. `isRunning` — отдельное поле.
Down появляется сразу после неудачного запуска; инцидент открывается только после
настроенного числа последовательных неудач. Error не открывает и не закрывает инцидент
и сбрасывает последовательность успехов/неудач.

Состояние Monitor: нет Check → Unknown; все на паузе → Paused; среди активных Check
приоритет Down → Error → Unknown → Up. Доля успешных запусков не усредняется по Monitor.

Статистика Check: успешные / (успешные + неуспешные) × 100. Внутренние ошибки исключены
из знаменателя и показаны отдельно. При отсутствии измерений процент и длительности
равны null, а не 100%. `durationMs` измеряется до получения заголовков; если задан
bodyContains — также включает чтение ограниченного тела. Это не uptime по времени.

## HTTP и защита

Только HTTP/HTTPS на портах 80/443. URL с логином/паролем и фрагментом запрещён.
Loopback, частные, link-local, служебные, multicast и некоторые зарезервированные
диапазоны IPv4/IPv6 запрещены. DNS проверяется при подключении: если хотя бы один
адрес запрещён, запрос блокируется; сокет подключается к проверенному IP.
TLS-сертификат проверяется стандартными средствами .NET.

Редиректы автоматически не выполняются: 301/302/307/308 проверяются как обычный
HTTP-статус. Для проверки конечной страницы укажите её конечный URL.
Cookie, системный proxy и автоматическая распаковка отключены. Текст ищется с учётом
регистра; тело ограничено 1 MiB, заголовки — 32 KiB. При bodyContains и неожиданно
сжатом ответе возвращается unsupported_encoding. Без bodyContains тело не загружается.
HEAD с bodyContains запрещён. Тела ответов не сохраняются; URL не пишутся стандартным
логгером HttpClient, чтобы параметры URL не попали в эти логи.

Коды результатов: unexpected_status, body_mismatch, timeout, dns_error, tls_error,
network_error, response_too_large, unsupported_encoding, blocked_target, internal_error.
Авторизация контролируется для всех операций, включая историю и отдельный результат.

## Планировщик и почта

В `appsettings.json`:

```json
"Monitoring": {
  "SchedulerEnabled": true,
  "MaxConcurrentRuns": 10,
  "PollIntervalSeconds": 5
}
```

Один лимит параллелизма используется ручными и автоматическими запусками внутри
экземпляра API. При нескольких экземплярах лимит суммируется, а lease одной Check
остаётся общей в PostgreSQL. Время всех серверов должно быть синхронизировано.
При перегрузке запуск может начаться позднее интервала. Это MVP, SLA и заявлений
о проверенной производительности нет. Backend должен постоянно работать.

Уведомления выключены по умолчанию. Включение у Monitor отправляет будущие события
на подтверждённый email владельца. Событие записывается в одной транзакции с инцидентом.
SMTP обрабатывается отдельно; максимум 5 попыток, интервалы повторов 1, 2, 4, 8 минут.
После пяти ошибок запись остаётся в БД с Attempts=5, ошибка записывается в лог.
Восстановление ждёт обработки уведомления о начале сбоя или исчерпания его попыток.
После отключения уведомлений ещё не отправленные события удаляются при обработке.
Сбой после SMTP-отправки, но до фиксации БД может привести к повторному письму.

Реальные SMTP-реквизиты в проект не добавлены. В тестах используется подменный sender;
доставка через реальный ящик отдельно не проверялась.

## Проверки и устройство кода

```sh
dotnet build Wubble.slnx
# Отдельная тестовая БД должна уже существовать:
WUBBLE_TEST_DB='Host=localhost;Database=wubble_tests;Username=wubble;Password=wubble' dotnet run --project Wubble.MonitoringChecks
WUBBLE_TEST_DB='Host=localhost;Database=wubble_tests;Username=wubble;Password=wubble' dotnet run --project Wubble.AuthChecks
```

В PowerShell задайте переменную перед запуском:
`$env:WUBBLE_TEST_DB = 'Host=localhost;Database=wubble_tests;Username=wubble;Password=wubble'`.
Наборы применяют миграции и удаляют только созданных ими пользователей и их данные.
HTTP-проверки используют управляемые ответы, поэтому тесты не зависят от сторонних сайтов.
Добавлен GitHub Actions workflow `tests.yml` с PostgreSQL 17.

- Monitoring/Models.cs, MonitoringConfiguration.cs — данные и EF-модель.
- MonitorsController.cs, ChecksController.cs — API и проверка владельца.
- HttpCheckExecutor.cs — сетевой запрос, SSRF и оценка ответа.
- CheckRunner.cs — lease, результат, состояние и инцидент в транзакции.
- MonitoringWorkers.cs — планировщик и доставка уведомлений.
- Wubble.MonitoringChecks — проверки HTTP API, PostgreSQL, SSRF, ошибок HTTP,
  истории, статистики, гонок запусков, инцидентов и повторов почты.

Совместный доступ Owner/Editor/Viewer, приглашения, папки, произвольные HTTP-методы,
заголовки/секреты, JSON-условия и браузерные сценарии остаются следующими задачами.
